# Fact table design and types

Fact tables store the quantitative performance measurements generated by
operational business events within a dimensional data warehouse. While dimension
tables supply descriptive context by answering who, what, where, and when,
fact tables contain foreign keys linking to those dimensions alongside numeric
metrics.

Selecting an appropriate fact table pattern determines how data pipelines
load records, how analytical queries compute aggregations, and how database
engines manage storage over time. Dimensional modeling identifies three
canonical fact table architectures: transaction fact tables, periodic snapshot
fact tables, and accumulating snapshot fact tables.

## When to use each fact table pattern

Use the following decision matrix to choose the appropriate fact table pattern:

| Pattern | Scenario | Key challenge | Design solution | Analytical trade-off |
| :--- | :--- | :--- | :--- | :--- |
| **Transaction fact table** | Student course registrations, tuition payments | Capturing point-in-time discrete events at maximum detail | Append-only rows linked to a single transaction date key | Queries aggregating long time horizons scan large volumes of atomic rows |
| **Periodic snapshot fact table** | Academic standing, quarterly cumulative Grade Point Average (GPA) | Tracking ongoing status and balances across recurring intervals | Generate dense periodic records at regular intervals with period-ending date keys | Users can't sum semi-additive metrics across the time dimension |
| **Accumulating snapshot fact table** | Admissions candidate lifecycles, financial aid approvals | Monitoring velocity and duration across defined multi-stage processes | Maintain one record per entity, updating role-playing milestone date keys in place | Requires row updates or partition rewrites in columnar storage systems |

## Core principles of fact table design

Fact table design requires following four foundational principles:
grain declaration, referential integrity, metric additivity, and sparsity
management.

### Grain declaration

The grain defines exactly what a single record in the fact table represents.
Every row in a given table must adhere to the exact same level of detail.

Ralph `Kimball` emphasizes declaring the grain at the lowest atomic level
captured by the operational source system, such as a single course registration
line. An atomic grain provides three operational advantages:

- Queries retain analytical flexibility because you can slice and aggregate data across any dimension without constraints from premature summarization.
- Tables preserve dimensional richness, whereas higher-level summary tables lose foreign key links to detailed dimensions (such as specific classroom locations or faculty advisors).
- Teams can answer unanticipated analytical questions directly by aggregating raw atomic measurements.

### Composite keys and referential integrity

A fact table contains foreign keys referencing the primary keys of surrounding
dimension tables. The combination of these foreign keys forms a composite
primary key that enforces row uniqueness and referential integrity.

Many data engineering teams also introduce a synthetic single-column surrogate
key, such as a hash-generated or sequence-based `fact_key`. This surrogate key
simplifies row identification in pipeline audit logs, distributed partitioning,
and query execution plans.

### Metric additivity types

Numeric measurements fall into three mathematical additivity classifications,
which dictate how SQL queries may aggregate them:

1. **Additive facts**: measurements that allow summation across all dimensions.
   Examples include `credit_units`, `tuition_amount`, and `discount_amount`.
   Additive metrics represent the most flexible measures in analytical models.
2. **Semi-additive facts**: measurements that allow summation across some
   dimensions, such as department or major, but not across the time dimension.
   Examples include `cumulative_units_earned` and `account_balance`. Summing
   yesterday's ending balance of \$500 with today's ending balance of \$600
   yields \$1,100, which produces a mathematically invalid total. Time-based
   summaries require point-in-time snapshots or averages.
3. **Non-additive facts**: measurements that prevent summation across any
   dimension. Examples include grade point averages, percentages, ratios, and
   unit fees. Queries must compute non-additive facts dynamically by dividing
   the sum of additive components, such as
   `SUM(total_grade_points) / SUM(credit_units)`.

### Sparsity versus density

Fact tables exhibit two contrasting data population patterns based on their
operational triggers:

- Sparse tables: transaction fact tables record rows only when an event occurs. If a student does not enroll in courses during the Summer quarter, the pipeline writes no row for that student.
- Dense tables: periodic snapshot fact tables record rows for every active entity at each scheduled interval, regardless of activity. If a university enrolls 15,000 students, a quarterly snapshot writes 15,000 rows at the close of each quarter, even if academic standing for most students remained unchanged.

## Canonical fact table architectures

`Kimball` dimensional modeling establishes three primary fact table designs.

### Transaction fact tables

Transaction fact tables represent operational events occurring at a discrete
point in time. The grain is one row per transaction event or transaction line.

A transaction fact table has the following characteristics:

- Append-only ingestion inserts rows when an event occurs and rarely modifies them once written.
- Rows link to a single transaction date or timestamp key in the calendar dimension.
- Dimensional sparsity remains high because records exist only for completed transactions.
- Numeric columns consist primarily of fully additive counts, units, and fee amounts.

### Periodic snapshot fact tables

Periodic snapshot fact tables capture the cumulative state, balance, or
performance of an ongoing process across uniform time intervals, such as daily,
weekly, or quarterly. The grain is one row per entity per period.

A periodic snapshot fact table has the following characteristics:

- Pipelines generate dense records for all monitored entities at the end of each period.
- Tables primarily track point-in-time balances and status scores alongside periodic activity totals using semi-additive metrics.
- Rows link to a single standardized period-ending date dimension record, such as `quarter_end_date_key`.

### Accumulating snapshot fact tables

Accumulating snapshot fact tables model the progress and velocity of an entity
moving through a multi-stage process with a defined start and finish. The grain
is one row per complete lifecycle of the entity.

An accumulating snapshot fact table has the following characteristics:

- Pipelines perform in-place updates on existing rows as the entity reaches successive milestones.
- Rows incorporate multiple role-playing date keys for each pipeline milestone (such as `submitted_date_key` and `reviewed_date_key`).
- Numeric columns compute the elapsed duration between milestone dates to measure process efficiency.

The following Mermaid diagram displays the milestone progression and duration
lags tracked within an admissions accumulating snapshot table:

## Schema implementation for the university scenario

The following schema demonstrates all three canonical fact table designs within
the Stanford University academic environment.

### Schema definitions

```sql
-- 1. Transaction fact table: student course enrollment
-- Grain: One row per student course enrollment per section
CREATE TABLE fact_course_enrollment (
    enrollment_id        BIGINT        NOT NULL,
    student_key          INT           NOT NULL REFERENCES dim_student(student_key),
    course_key           INT           NOT NULL REFERENCES dim_course(course_key),
    section_key          INT           NOT NULL REFERENCES dim_course_section(section_key),
    term_key             INT           NOT NULL REFERENCES dim_term(term_key),
    enrollment_date_key  INT           NOT NULL REFERENCES dim_date(date_key),
    
    -- Fully additive measures
    enrollment_count     INT           NOT NULL DEFAULT 1,
    enrolled_units       INT           NOT NULL,
    tuition_amount       DECIMAL(10,2) NOT NULL,
    grade_points_earned  DECIMAL(4,2),
    
    PRIMARY KEY (enrollment_id)
);

-- 2. Periodic snapshot fact table: quarterly student academic status
-- Grain: One row per student per academic quarter
CREATE TABLE fact_student_quarter_snapshot (
    term_end_date_key    INT           NOT NULL REFERENCES dim_date(date_key),
    student_key          INT           NOT NULL REFERENCES dim_student(student_key),
    major_department_key INT           NOT NULL REFERENCES dim_department(department_key),
    
    -- Semi-additive balances (valid across departments, not across terms)
    cumulative_gpa       DECIMAL(3,2)  NOT NULL,
    cumulative_units     INT           NOT NULL,
    
    -- Additive quarterly activity summaries
    quarter_units_earned INT           NOT NULL,
    quarter_tuition_paid DECIMAL(10,2) NOT NULL,
    
    PRIMARY KEY (term_end_date_key, student_key)
);

-- 3. Accumulating snapshot fact table: admissions candidate pipeline
-- Grain: One row per student admissions lifecycle
CREATE TABLE fact_admissions_application (
    application_id       BIGINT        NOT NULL,
    applicant_key        INT           NOT NULL REFERENCES dim_student(student_key),
    department_key       INT           NOT NULL REFERENCES dim_department(department_key),
    
    -- Role-playing milestone date keys (default to placeholder -1 for pending)
    submitted_date_key   INT           NOT NULL REFERENCES dim_date(date_key),
    verified_date_key    INT           NOT NULL REFERENCES dim_date(date_key),
    reviewed_date_key    INT           NOT NULL REFERENCES dim_date(date_key),
    decision_date_key    INT           NOT NULL REFERENCES dim_date(date_key),
    enrolled_date_key    INT           NOT NULL REFERENCES dim_date(date_key),
    
    -- Milestone duration metrics
    days_to_verify       INT,          -- verified_date - submitted_date
    days_to_review       INT,          -- reviewed_date - verified_date
    days_to_decision     INT,          -- decision_date - reviewed_date
    total_pipeline_days  INT,          -- decision_date - submitted_date
    
    PRIMARY KEY (application_id)
);
```

### Query department enrollment from transactions

The following query calculates total enrolled students, credit units, and
tuition revenue grouped by academic department:

```sql
SELECT 
    d.department_name,
    COUNT(f.student_key)     AS total_enrollments,
    SUM(f.enrolled_units)    AS total_credit_units,
    SUM(f.tuition_amount)    AS total_tuition_revenue
FROM fact_course_enrollment AS f
JOIN dim_course AS c
    ON f.course_key = c.course_key
JOIN dim_department AS d
    ON c.department_key = d.department_key
WHERE f.enrollment_date_key BETWEEN 20260901 AND 20261231
GROUP BY d.department_name
ORDER BY total_tuition_revenue DESC;
```

### Query student performance distribution from periodic snapshots

The following query calculates average cumulative GPA and student counts by
major department for the Autumn 2026 quarter:

```sql
SELECT 
    d.department_name,
    COUNT(snap.student_key)  AS active_student_count,
    AVG(snap.cumulative_gpa) AS average_cumulative_gpa
FROM fact_student_quarter_snapshot AS snap
JOIN dim_department AS d
    ON snap.major_department_key = d.department_key
WHERE snap.term_end_date_key = 20261215 -- Autumn 2026 term end
GROUP BY d.department_name
ORDER BY active_student_count DESC;
```

### Query admissions review velocity from accumulating snapshots

The following query calculates average processing durations across admissions
milestones by department:

```sql
SELECT 
    d.department_name,
    COUNT(app.application_id) AS total_applications_processed,
    AVG(app.days_to_verify)   AS avg_days_to_verify,
    AVG(app.days_to_review)   AS avg_days_to_review,
    AVG(app.days_to_decision) AS avg_days_to_decision,
    AVG(app.total_pipeline_days) AS avg_total_pipeline_days
FROM fact_admissions_application AS app
JOIN dim_department AS d
    ON app.department_key = d.department_key
WHERE app.decision_date_key <> -1 -- Exclude pending admissions records
GROUP BY d.department_name
ORDER BY total_applications_processed DESC;
```

## Operational considerations and engine optimization

When implementing fact table designs in modern data warehouses such as
`BigQuery`, consider the following technical factors:

- Partition transaction fact tables by their primary date key (such as
  `enrollment_date_key`). Cluster tables by frequently filtered foreign keys
  (such as `department_key` or `student_key`) to enable efficient block pruning
  during queries.
- Accumulating snapshots require row updates as entities reach milestones. In
  columnar architectures such as `BigQuery` or `Parquet`-backed data lakes,
  frequent single-row updates cause high write amplification. Batch updates using
  scheduled merge jobs or adopt a snapshot-and-append transformation pattern.
- In accumulating snapshots, pending milestones do not have a valid date. Avoid
  populating SQL null values, which drop rows during inner joins. Instead,
  reference designated placeholder dimension records (such as `-1` for
  `Pending` or `-2` for `Not Applicable`).

## Common pitfalls

When designing fact tables, watch for these common mistakes:

### Storing SQL null foreign keys

Data pipelines sometimes populate SQL null values in foreign key columns when an
attribute is unknown or pending. Equality comparisons against null values
evaluate to unknown because `NULL = NULL` yields unknown. Consequently, standard
inner joins between the fact table and dimensions silently drop rows from
analytical reports. Always use integer sentinel keys such as `-1` to represent
missing or pending dimensions.

### Building centipede fact tables

A centipede fact table occurs when schema designers split correlated attributes
into dozens of small lookup dimensions, resulting in 25 to 50 foreign keys in a
single fact table. This bloats row width, exceeds optimizer join thresholds,
and complicates query generation. Collapse correlated attributes into wide,
`` `denormalized` `` dimension tables.

### Normalizing facts into entity-attribute-value rows

Fact normalization occurs when engineers attempt to normalize a fact table by
replacing distinct numeric columns with a generic `metric_type_key` and a single
`metric_value` column. This multiplies the row count by the number of metrics.
Computing intra-row calculations, such as subtracting discounts from gross
tuition, requires expensive self-joins or conditional aggregations.

### Storing pre-computed ratios directly in fact rows

Storing calculated ratios, such as grade point averages or discount percentages,
directly in fact rows violates atomic grain principles. Because SQL `SUM()`
operations aggregate across rows, summing pre-computed ratios produces invalid
results. Store additive components in the fact table and compute ratios
dynamically in queries.
